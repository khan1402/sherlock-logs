# Sherlock Logs

A small web infrastructure built **fully as code** (Vagrant + Ansible + Jenkins + a FastAPI
app), with **monitoring, logging and alerting**. A dedicated VM runs Prometheus, Grafana and
the ELK stack. Every VM has agents for metrics and logs, alerts go to Slack, and the
Jenkins pipeline tests, builds and deploys the app and keeps the agents up to date.

**One command builds everything from an empty laptop, with no manual steps.**

```powershell
.\scripts\up.ps1 -Fresh
```

All VMs use 1 vCPU (2 vCPUs hang at boot on this laptop, see the notes).

**Agents on every VM:**
- **Node Exporter** (port 9100): CPU, memory, disk, network of the VM.
- **cAdvisor** (port 8081, Docker VMs only): CPU, memory and restarts of every container.
- **Filebeat**: sends system logs, auth logs, container logs and nginx logs to Logstash.

**The app** also exposes its own metrics on `/metrics` (Prometheus client library):
request count, response time, the custom histogram `metrics_collect_seconds` and the
custom counter `frontend_backend_errors_total`. It writes its logs as JSON.

## 2. How monitoring and logging work

**Metrics (pull):** every 15 s, Prometheus pulls metrics from Node Exporter, cAdvisor,
the app and the Elasticsearch exporter. Grafana shows them on 3 dashboards and checks
13 alert rules every 30 s.

**Logs (push):** Filebeat on every VM pushes new log lines to Logstash. Logstash parses
them (grok, json, date), stores them in Elasticsearch (2 nodes, every index stored twice)
and sends log-pattern alerts to Slack. Kibana shows them on 3 dashboards.

**Alerts:** Grafana alerts and Logstash log alerts go to Slack, with grouping and
throttling against alert fatigue.

**Retention:** Prometheus keeps metrics for 15 days or 5 GB. An Elasticsearch ILM policy
deletes log indices older than 14 days. Both values are in
`ansible/roles/monitoring/defaults/main.yml`.

## 5. Run it

All commands from the repo folder.

| What | Command (PowerShell) | Time |
|---|---|---|
| Build everything from a blank slate | `.\scripts\up.ps1 -Fresh` | 60–120 min (mostly downloads) |
| Same, with the bonus features | `.\scripts\up.ps1 -Fresh -Bonus` | 60–120 min |
| Start existing VMs (after a shutdown) | `.\scripts\up.ps1` | ~3 min |
| Shut everything down cleanly | `.\scripts\down.ps1` | ~1 min |
| Delete all VMs | `.\scripts\down.ps1 -Destroy` | ~1 min |

`ansible/site.yml` configures all VMs in this order: patches → hardening → firewall →
Docker → **monitoring agents** → **monitoring stack** → app images → app deploy →
load balancer → Jenkins. The monitoring stack comes up **before** the app, so it already
watches the first deploy.

To re-apply only the monitoring stack (about 3 minutes), on cicd-server:

```bash
ssh -i keys/ansible_key devops@192.168.56.14          # Git Bash, then on cicd-server:
bash /vagrant/scripts/sync-to-cicd.sh
cd ~/sherlock-logs/ansible && ansible-playbook site.yml --tags monitoring -e enable_bonus=true
```

## 6. Check it

```bash
bash scripts/validate.sh --bonus     # Git Bash: 209 checks
```

Read-only. For every VM it checks hostname, IP, name resolution, sudo, umask, SSH policy,
firewall ports, pending security updates and the VM's services. On the monitoring VM it
checks that Prometheus, Grafana, Kibana and Logstash answer, Elasticsearch is green with
2 nodes, and **every Prometheus target is UP**. From the laptop, it proves that root and
password logins are refused, the app answers through the load balancer, and that the web
servers, the app server, Elasticsearch, Logstash, Node Exporter and cAdvisor can **not**
be reached directly.

## 8. Alerts

All rules live in one list: `monitoring_alert_rules` in `ansible/roles/monitoring/defaults/main.yml`.

| Alert | Fires when | Wait | Level |
|---|---|---|---|
| High CPU usage | CPU above 80% | 5 min | warning |
| High memory usage | memory above 90% | 5 min | warning |
| Low disk space | less than 20% free on `/` | 1 min | critical |
| Container restarting | more than 3 restarts in 15 min | — | warning |
| Container near its memory limit | above 80% of its own limit | 1 min | warning |
| VM unreachable | Node Exporter can't be scraped | 1 min | critical |
| Elasticsearch cluster yellow or red | cluster not green | 1 min | critical |
| Elasticsearch unreachable | exporter can't read the cluster | 1 min | critical |
| Application instance down | backend or frontend can't be scraped | 1 min | critical |
| Application error rate high | more than 5% of requests fail (5xx) | 2 min | critical |
| *Advanced:* Disk will be full within 4 hours | `predict_linear` of free space | 5 min | warning |
| *Advanced:* CPU usage rising steadily | `deriv`: +40 points in 30 min | 5 min | info |
| *Advanced:* High CPU and low memory together | CPU > 80% **and** free memory < 10% | 2 min | critical |

**Log-pattern alerts (Logstash):** a failed SSH login (`Failed password` or `Invalid user`)
and an app error (level `ERROR`/`CRITICAL`, or an nginx error) are sent to Slack.

**Against alert fatigue:** one Slack message per alert type and VM (`group_by`), 30 s
`group_wait`, 5 min `group_interval`, a reminder only every 4 h (`repeat_interval`), and a
*Resolved* message when the problem is gone. Logstash sends at most one message per VM
and alert type every 5 minutes.

## 9. Testing the alerts

Ready-made scripts in `scripts/demo/` (Git Bash, from the laptop). Each one prints what to
expect and where to look. Run them one at a time on a web server.

| Test | Start | Slack after | Clean up |
|---|---|---|---|
| CPU > 80% for 5 min | `bash scripts/demo/cpu.sh web-server-1` | ~6 min | stops by itself (6 min) |
| Memory > 90% for 5 min | `bash scripts/demo/memory.sh web-server-1` | ~6 min | stops by itself (6 min) |
| Disk < 20% free | `bash scripts/demo/disk.sh web-server-1` | ~2 min | `bash scripts/demo/disk.sh web-server-1 stop` |
| Container restarts | `bash scripts/demo/container-restarts.sh web-server-1` | ~3–4 min | `... container-restarts.sh web-server-1 stop` |
| Container memory > 80% | `bash scripts/demo/container-memory.sh web-server-1` | ~2–3 min | `... container-memory.sh web-server-1 stop` |
| VM unreachable | `bash scripts/demo/vm-down.sh web-server-1` | ~2 min | comes back by itself (150 s) |
| Elasticsearch yellow | `bash scripts/demo/es-yellow.sh` | ~2 min | `bash scripts/demo/es-yellow.sh restore` |
| Failed SSH login (log alert) | `ssh wronguser@192.168.56.11` | ~30 s | — |

**Demo mode** shortens the 5-minute waits to 1 minute (thresholds stay the same):
`bash scripts/demo/demo-mode.sh on`, and `off` afterwards.

## 10. The pipeline

Jenkins checks Git every minute. For each new commit:

| # | Stage | Fails the build when |
|---|---|---|
| 1 | Version | — image tag = short commit ID |
| 2 | Code checks | Ruff, Bandit or a unit test fails |
| 3 | Build images | Docker build fails |
| 4 | Image scan | Trivy finds a CRITICAL vulnerability with a fix |
| 5 | Push to Docker Hub | push fails 3 times |
| 6 | **Monitoring agents** | `monitoring-agents.yml` fails: Node Exporter, cAdvisor and Filebeat on every VM |
| 7 | **Monitoring check** | a target is down, Elasticsearch isn't green, no logs in 15 min, or a dashboard / alert rule is missing |
| 8 | Deploy | Ansible `deploy.yml`, rolling |
| 9 | Smoke test | the app doesn't answer correctly through the load balancer |
| 10 | Load test | k6: > 1% errors or p95 > 2.5 s |

A new VM in the inventory gets its agents on the next build, and Prometheus adds it as a
target. The pipeline never deploys blind: if monitoring is broken, the deploy doesn't start.

## 11. Secrets

All secrets live in `ansible/group_vars/all/vault.yml`, encrypted with Ansible Vault:
the devops password, Docker Hub token, Jenkins and Grafana admin passwords and the Slack webhook.

- `.vault_pass` and `keys/` are in `.gitignore` and never committed.
- The Slack webhook is never written into Logstash's config: Logstash reads it from an
  environment variable. Grafana's contact-point file is readable only by root and Grafana.
- Ansible tasks that handle secrets use `no_log: true`.

To read the Grafana password without showing the whole vault (on cicd-server):

```bash
cd ~/sherlock-logs/ansible && ansible-vault view group_vars/all/vault.yml | grep grafana
```

## 12. Bonus and extras

- **2-node Elasticsearch cluster:** every index has a replica on the other node.
- **Advanced alerts:** trend (`predict_linear`, `deriv`) and combination (`and on (instance)`) rules.
- **Log-pattern alerts** from Logstash, with throttling.
- **Dashboards as code** (`scripts/build-dashboards.py`) and a monitoring health check in Jenkins.
- **Backup server** (pull model, daily, 7 days) and **Fail2Ban** on every VM.
- **Firewall:** monitoring ports accept only the monitoring server; Elasticsearch is bound
  to the monitoring VM's loopback and can't be reached from the network.

## 14. Review checklist

1. `.\scripts\up.ps1 -Fresh -Bonus` — wait for *Ready*.
2. `bash scripts/validate.sh --bonus` — expect `ALL 209 CHECKS PASSED`.
3. Prometheus <http://192.168.56.16:9090/targets> — 17 targets, all UP.
4. Grafana — the 3 dashboards show data (run the traffic loop for the app dashboard).
5. Kibana — the 3 log dashboards; search `system.message:"Invalid user"` after a failed SSH login.
6. Jenkins → `sherlock-logs` — the last build is green, including *Monitoring agents* and *Monitoring check*.
7. Run the alert tests in section 9 and show the Slack messages and the *Resolved* messages.
8. Re-run `ansible-playbook site.yml` on cicd-server → `changed=0` (only new Ubuntu patches may show up).
