# Project notes — Sherlock Logs

Why the monitoring and logging setup is built the way it is, what went wrong while
building and testing it, and how each problem was fixed. For the overview see the
[README](../README.md); for diagrams see [architecture_project-4.md](architecture_project-4.md).

---

## 1. Key design decisions

| Decision | Why |
|---|---|
| **Monitoring on its own VM** | Monitoring must survive when an app VM is overloaded or down. It also keeps the heavy Java services away from the small app VMs. |
| **Prometheus pull for metrics, Filebeat push for logs** | Pull makes a missing VM visible at once (target DOWN). Logs are produced all the time, so the VM pushes them, and Filebeat resends what Logstash missed. |
| **Scrape targets and agent configs generated from the inventory** | A new VM is one inventory entry. Prometheus targets, Filebeat inputs and firewall rules follow automatically. |
| **Agents in a separate playbook** (`monitoring-agents.yml`) | Used by `site.yml` and by the Jenkins pipeline, so every build keeps the agents up to date. |
| **The stack in Docker Compose, versions pinned** | One file describes the whole stack. An upgrade is a version number change and an Ansible run. |
| **2 Elasticsearch nodes, 1 replica per index** | Every log is stored twice; one node can stop without losing data (the yellow-state test). es02 is data-only, so there's no vote between two equal masters. |
| **Elasticsearch on loopback only** | Only Logstash, Kibana and the exporter need it. Nobody on the network can read or delete the logs. |
| **Unparsed log lines are kept, with a tag** | Nothing is lost when a format changes. `tags : *_failure` in Kibana shows what to fix. |
| **Alert rules as one list in Ansible** (`monitoring_alert_rules`) | Every threshold and wait time is in one place, reviewed in Git, and re-applied with one command. |
| **Dashboards generated by a script** (`build-dashboards.py`) | Dashboards are code: reproducible, reviewable, no clicking. They are read-only in Grafana. |
| **`for` wait times + grouping + 4 h repeat** | Short spikes never alert, one problem gives one message, and reminders don't flood Slack. |
| **Demo mode** (5 min → 1 min, thresholds unchanged) | The review is short. Normal operation keeps the real 5-minute windows. |
| **Monitoring check before every deploy** | Never deploy blind: if the monitoring is broken, Jenkins stops before the deploy. |
| **Small memory limits** (ES 512 MB heap / 1 GB, Logstash 256 MB / 640 MB, Kibana 512 MB) | Everything must fit on a 16 GB laptop. The defaults file notes the values for a bigger host. |

## 2. Incidents and fixes

Each one happened for real while building and testing. They're listed in order.

### 1. monitoring-server hung at boot with 2 vCPUs
- **Problem:** with 2 vCPUs, the VM froze during boot. The laptop runs VirtualBox next to Hyper-V/WSL2.
- **Fix:** `vm_cpus: 1`. The monitoring VM got more RAM instead.

### 2. Logstash config check failed: "Initial heap size larger than max"
- **Problem:** the validation run set only `-Xmx256m`, but the image starts with a 1 GB minimum heap.
- **Fix:** the check passes both `-Xms256m -Xmx256m`.

### 3. Filebeat install refused a downgrade
- **Problem:** apt had already installed a newer Filebeat than the pinned 8.19.2, and refused to go back.
- **Fix:** `allow_downgrade: true`, then the package is held (`dpkg_selections: hold`), so updates don't move it again.

### 4. Grafana stuck in a restart loop
- **Problem:** the contact-point file (with the Slack webhook) was owned by group 472. Grafana runs as uid 472 but with **group 0**, so it couldn't read the file.
- **Fix:** `group: root`, `mode: "0640"` — readable by root and Grafana only.

### 5. cAdvisor always "unhealthy"
- **Problem:** the image's built-in health check asks port 8080, but cAdvisor runs on 8081 in this project.
- **Fix:** a health check override on `/healthz` at port 8081.

### 6. Jenkins "Monitoring agents" stage hung for 2 hours
- **Problem:** on cicd-server, Ansible connects locally as the `jenkins` user, which has no sudo there (on purpose). The play waited for a sudo password forever.
- **Fix:** the stage runs with `--limit all:!cicd`. cicd-server's own agents come from `site.yml`. A build shouldn't restart services on its own server anyway.

### 7. web-server-1 froze from out-of-memory
- **Problem:** with 640 MB, the frontend + cAdvisor + Filebeat + a Filebeat install filled the RAM, and the next Jenkins task hung for 25 minutes.
- **Fix:** web servers 768 MB, app-server 1 GB. The running VMs were resized with `VBoxManage modifyvm --memory`, without a rebuild.

### 8. Demo mode removed backup-server from Prometheus
- **Problem:** re-applying the monitoring stack without `enable_bonus=true` regenerated the target list without the bonus VM.
- **Fix:** `demo-mode.sh` checks whether backup-server exists and passes `-e enable_bonus=...`.

### 9. Random "rc -13" SSH errors on a fresh build
- **Problem:** Ansible's shared SSH connections closed while tasks still used them.
- **Fix:** `forks = 10` and `ControlPersist=30m` in `ansible.cfg`.

### 10. The first backup skipped app-server
- **Problem:** the first backup ran only when *no* VM had an archive yet.
- **Fix:** it runs when **any** VM has no archive.

### 11. Jenkins: "No system logs in the last 15 minutes"
- **Problem:** after the timezone change, rsyslog kept writing in UTC, so the logs were stored 2 hours in the past and the health check found nothing recent.
- **Fix:** a "Restart rsyslog" handler on the timezone task.

### 12. Docker Containers dashboard empty (Docker 29)
- **Problem:** Docker 29 stores images in containerd by default. cAdvisor 0.49.1 can't read that store, so its metrics had no container names, and the dashboard and the container alerts were empty.
- **Fix:** `"features": {"containerd-snapshotter": false}` in `daemon.json` (docker role). Docker went back to overlay2, and every container name appeared again. The first run after the change re-downloaded all images (about 2 hours on this laptop).

### 13. "Failed SSH logins" panel was always empty
- **Problem:** the panel searched for `Failed password`, but password login is off in this project. A wrong user is logged as `Invalid user ...`.
- **Fix:** the panel (and the Logstash alert) match `Failed password` **or** `Invalid user`.

### 14. Demo scripts said "started", but nothing happened
- **Problem:** `vm-down.sh` and `memory.sh` started their job in the background over SSH. Closing the SSH session also stopped the job, so the network never went down and the memory never filled.
- **Fix:** the job runs as a short systemd service (`systemd-run`), outside the SSH session. `memory.sh` also needed `--temp-path /tmp`, because a service starts in `/`, where stress-ng can't write.

### 15. "Container restarting" never fired
- **Problem:** cAdvisor's `container_start_time_seconds` is the container's **creation** time. A container restarted by `--restart=always` keeps it, so `changes()` always returned 0 (Docker counted 31 restarts).
- **Fix:** every restart starts a new CPU counter at 0, so the rule counts those drops: `resets(container_cpu_usage_seconds_total[15m]) > 3`. The dashboard uses the same query.

### 16. "Container near its memory limit" firing for hours
- **Problem:** es01, es02 and Logstash always sit at 95–100 % of their limits. Java reserves its whole heap at start, and Elasticsearch keeps index files in memory. That's by design, not a problem.
- **Fix:** the rule and the dashboard box skip `es0[0-9]|logstash`. Elasticsearch health has its own alerts (yellow/red, unreachable).

### 17. The container memory test froze web-server-1
- **Problem:** a 256 MB test container using 220 MB was too much for a 768 MB VM: "VM unreachable" fired and SSH timed out.
- **Fix:** the test container is 128 MB with 110 MB used — still above 80 %, but safe.

## 4. Known limits and warnings

- **The monitoring VM is tight on memory** (about 90 % used). The *High memory usage* alert for monitoring-server can flap around 90 %. On a real server it would get more RAM, or a per-VM threshold.
- **One monitoring VM** is a single point of failure for monitoring. Both Elasticsearch nodes run on it, so the 2-node cluster protects against a crashed node, not a crashed VM.
- **Slack links point to `http://localhost:3000`.** Grafana's public URL (`root_url`) isn't set; open Grafana at `http://192.168.56.16:3000` instead.
- **No escalation routing:** every alert goes to one Slack channel. The severity is in the title; a bigger team would route critical alerts to an on-call tool.
- **cAdvisor 0.49.1 needs the classic Docker image store.** When a cAdvisor release supports Docker 29's containerd store, the `daemon.json` setting can go.
- **The Java services are not covered by the container memory alert** (incident 16).
- **Container restarts are counted from CPU counter resets.** A restart between two scrapes (15 s) can be missed; a real crash loop is always caught.
- **The Application Performance dashboard needs traffic.** With no visitors, there's nothing to draw.
- **Demo scripts ask for the devops sudo password** (they run Docker and systemd-run on the VM).
- **The *Monitoring check* stage fails while Elasticsearch is yellow.** That's on purpose, but don't push a commit during the yellow-state test.
- **HTTP only:** no TLS on the app, Jenkins, Grafana, Kibana or Prometheus. Acceptable on a private host-only network.
